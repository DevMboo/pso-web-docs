Request and response lifecycle

The exact order in which the orchestrator handles an HTTP request, which status each stage can answer, what is logged, and how to find the stage that rejected a request.

What this page answers#

When a request does not do what you expect, the first question is which stage said no. The answer is always in the status code, the code member of the error body and one log line. This page lists the stages in the order they run, so you can read an answer backwards to its cause.

The stages, in order#

#StageWhat it checksOutcome when it fails
1Correlationaccepts an incoming x-correlation-id when it is 8 to 64 characters of A-Z a-z 0-9 . _ -; otherwise generates a UUID (so even a refused request has an id)never fails; a malformed id is replaced, never echoed
2Limits and rate limitconnection and concurrency limits, header size, the token bucket for the client (and route, and principal when configured)431, 503 server_busy, 429 with Retry-After and RateLimit-* headers
3Route registrythe method and path are declared in ROUTES.pso.ts and the controller is registered404 for anything not declared, including decorated but undeclared methods
4Authenticationa valid token for guarded routes401 with WWW-Authenticate: Bearer
5Authorizationthe scopes or roles the route requires403
6Middlewareyour middleware, only for requests that passed the guardswhatever your middleware sends
7Body and parameterssize limit, application/json, valid JSON, then the @Dto rules and any @Param/@Query descriptions413, 415, 400 invalid_json, 400 PSO_VALIDATION_FAILED with a field list
8Actionyour code200 (201 for POST) with the returned value, the status of a thrown HttpError, otherwise 500 (nothing internal is returned)
9Upstream (when the action forwards)the service is known, reachable and answers in time502 unknown service or invalid answer, 503 unreachable, 504 timeout
10Responseheaders added to every answer, one log line
Note

The order differs from some frameworks on purpose. Middleware runs after the guards, so it never processes an unauthenticated request on a guarded route. Validation runs after authorization, so an anonymous caller cannot probe the shape of your bodies. Rate limiting runs first because it is the cheapest way to refuse work.

Every response#

  • x-correlation-id: the same value that appears in the error body (correlationId) and in the log line.
  • Errors are application/problem+json with a stable code (error standard). A client-supplied correlation id is used only if it is well-formed; a value that is not is replaced with a generated one.
  • One log line per request with the method, path, status, duration and trace id (never the body, headers or tokens). On a terminal:

In production the same event is one JSON line (logging).

Example: one request through every stage#

  1. Correlation: trace-me-0001 is well-formed, so it is kept.
  2. Rate limit: allowed (RateLimit-Remaining is in the response headers).
  3. Route registry: POST /orders is declared.
  4. Authentication and authorization: the token is valid and carries orders:write.
  5. Body: JSON object, within the size limit.
  6. Validation: three fields break their rules. The action is not called.

Find the stage from the answer#

You seeThe stage that answeredLook at
429rate limitRetry-After; the limits in pso.config.json (rate limiting)
404 with PSO_HTTP_NOT_FOUNDroute registrypso routes:list: the method and path must be declared
401authenticationthe token, issuer, audience and algorithms; the start-up line security initialized
403authorizationthe scopes the route declares versus the scopes in the token
400 + errorsvalidationthe field names in errors
400 + invalid_json / 415 / 413body parsingcontent type, JSON syntax, http.limits.maxBodyBytes
500your actionthe response never contains the cause. In this version the log has only the request ... status=500 line with the correlation id (verified: no message or stack is logged for an unexpected error), so reproduce it, or catch and log inside the action with log("error", ...) from @pso/http
502 / 503 / 504upstreamwhether the service is running at the address in pso.workspace.json; its own logs with the same correlation id

Anti-patterns#

  • Validating authentication inside an action: use a guard, so the decision happens at stage 4 and appears in the same place for every route.
  • Throwing HttpError for conditions the framework already covers (a missing field is a validation problem, not new HttpError(400, ...)).
  • Returning internal error text to "help" the caller. The 500 body is deliberately generic. Note that the runtime does not log the cause either, so log it yourself where you can add context (never the request body or a token).

Troubleshooting#

What you seeWhich stage answeredHow to tell
401, 403the gateway, before any serviceinstance is the public path (/products), and the gateway log has a warn line for 403
400 PSO_VALIDATION_FAILED with instance /catalog/...the service validated and the gateway passed the answer throughthe /catalog prefix in instance
404 with instance not starting with the prefixthe gateway has no such routepso routes:list
404 with the service prefixthe service answeredthe id or path
500 PSO_INTERNAL_ERRORan unexpected error in the service, with no cause in the bodythe service log under the same correlationId

All five were observed in Build a CRUD API. A response's x-correlation-id and the correlationId of its error body are the same id: search the logs for it.
