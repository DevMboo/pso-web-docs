Remote service clients

Forward requests to Spring Boot services with the built-in Upstream provider.

with metadata: { service: "catalog" } on the route. forward refuses a service that differs from the route's declared one, so the route registry stays the single source of truth.

Where services come from#

EnvironmentSource
Developmentpso.workspace.json (the services' port, on 127.0.0.1)
ProductionPSO_UPSTREAM_<NAME>=host:port, e.g. PSO_UPSTREAM_CATALOG=catalog:8081 (what the generated Compose file sets)

Nothing scans ports. A malformed host:port stops start-up. Discovery never implies authorization: the route's guard decides who may call.

Request hygiene#

  • Client x-pso-*, x-forwarded-for and x-correlation-id headers are dropped; a fresh correlation id is sent.
  • Authorization is forwarded only on guarded routes, so the service validates the token itself.
  • Hop-by-hop headers are removed; the upstream timeout (UPSTREAM_TIMEOUT_MS, default 5 s) and body limit apply.
  • If an action consumed the body with @Body(), the raw body is re-sent. Actions generated by make:route --upstream and make:resource do not consume it.

Failure modes#

SituationResponse
Upstream refused the connection or cannot be resolved503 upstream_unavailable
Upstream timed out (connect, idle or total deadline)504 upstream_timeout
Upstream reset the connection or sent an invalid response502 bad_gateway
Upstream response larger than MAX_UPSTREAM_RESPONSE_BYTES (declared length)502 upstream_response_too_large
Request body larger than MAX_BODY_BYTES413 payload_too_large
Service name not registered502 unknown_service
Route and action disagree on the service500 (a programming error)

There are no automatic retries or circuit breakers in this version.

Limits#

Limits are read from environment variables at start-up and validated; an invalid value stops the process and names the variable. Streaming is enforced while bytes flow, so memory stays bounded.

VariableDefaultMeaning
MAX_BODY_BYTES1048576request body; checked from Content-Length and while streaming
MAX_UPSTREAM_RESPONSE_BYTES10485760upstream response body
MAX_HEADER_BYTES16384request line plus headers (431 when exceeded)
UPSTREAM_TIMEOUT_MS5000connect and idle time of an upstream socket
UPSTREAM_RESPONSE_TIMEOUT_MS30000deadline for the whole upstream exchange
HEADERS_TIMEOUT_MS / REQUEST_TIMEOUT_MS / KEEP_ALIVE_TIMEOUT_MS10000 / 30000 / 5000client-side timeouts
MAX_CONNECTIONS1000open connections
MAX_CONCURRENT_REQUESTS0 (unlimited)above this, requests get 503 server_busy with Retry-After
MAX_UPLOAD_BYTES10485760a whole multipart/form-data request, counted while it streams (a DTO's own file limits apply inside it)
MAX_MULTIPART_PARTS50parts (fields and files) of one multipart request
MAX_CONCURRENT_UPLOADS16 (0 = unlimited)uploads being received at once; above this 503 server_busy with Retry-After

When an upstream response exceeds the limit after headers were sent (chunked streams), a second status is impossible: the stream is closed abnormally, the upstream transfer is terminated and a warning is logged. A client that disconnects cancels the upstream request. With NODE_ENV=production a critical limit set to more than 100 times its default is refused.

Each limit is also a configuration key (http.limits.maxBodyBytes, http.limits.maxUpstreamResponseBytes, http.limits.upstreamTimeoutMs, ...) that can be set in pso.config.json, per environment in pso.config.<environment>.json, or with PSO_CFG_http__limits__<name>; the variable in the table always wins. See Rate limiting for the precedence rules and http.rateLimit.*.

TLS, mutual TLS, credential-forwarding policy per upstream and certificate rotation are described in Service identity and mutual TLS.

Uploads and downloads#

forward() relays the request exactly as it arrived. Files get two dedicated methods, both on the same Upstream provider, both bound to the route's declared metadata.service:

MethodUseWhat it guarantees
forwardUpload(req, res, service, dto, { path })the DTO was bound with @Body(Dto) and has @FileField fieldsa new multipart request is built from the validated fields and files (nothing of the client's body, Content-Type, boundary or identity headers is relayed), streamed from the temporary files with an exact Content-Length; correlation, trace and the credentials your upstream policy allows travel as in forward()
forwardDownload(req, res, service, { path, maxResponseBytes })stream a stored file to the clientbackpressure both ways, abort on client disconnect, a per-route size cap (default MAX_UPSTREAM_RESPONSE_BYTES), and on 2xx responses X-Content-Type-Options: nosniff, Content-Security-Policy: sandbox, Cache-Control: private, no-store and Content-Disposition: attachment unless the service chose one

See File uploads and downloads for a complete example.

What the caller sees#

When the upstream behaves, the gateway is transparent. When it does not, the answer is a standard problem with a stable code (verified for the unavailable case):

Upstream conditionAnswer
answersthe upstream's status and body
connection refused (service down)503 PSO_UPSTREAM_UNAVAILABLE
does not answer in time504 PSO_UPSTREAM_TIMEOUT
unknown service name502 PSO_UPSTREAM_UNKNOWN_SERVICE
invalid or oversized answer502 (PSO_UPSTREAM_BAD_GATEWAY, PSO_UPSTREAM_RESPONSE_TOO_LARGE)
TLS verification failed502 PSO_UPSTREAM_TLS

Troubleshooting a forward#

  1. pso services:health: is the service up? (verified output: DOWN catalog http://127.0.0.1:8081/actuator/health).
  2. pso routes:inspect <route>: does the route point at the service and port you expect?
  3. In production, is PSO_UPSTREAM_<NAME>=host:port set (the service name in upper case, hyphens as underscores)?
  4. Read the service's own log with the same correlation id: the orchestrator forwards x-correlation-id.
  5. For timeouts, compare http.limits.upstreamTimeoutMs with the service's real latency before raising it.

Composing a response from several services: UpstreamClient#

Upstream.forward hands the current request to one service. An action that needs data from several services (a customer summary built from the customers, orders and catalog services) uses UpstreamClient instead: it calls registered services by name and the action builds the response. The orchestrator coordinates; the business rules stay in the services.

The generator injects the client and, in ROUTES.pso.ts, declares the services the action may call:

RuleDetail
Destinationthe name of a registered service; there is no URL parameter. The path is relative to the service, and its endpoint prefix is applied once, by the client
Declarationinside a request the service must be listed in the route's metadata.services (or be its metadata.service). A call to any other service is refused before anything is sent (PSO_UPSTREAM_POLICY, and the log names the missing declaration). pso validate refuses a name that is not a service of the workspace (PSO_ROUTE_010)
Path and query:name segments are replaced from params, each encoded as one segment; .., //, ?, # and encoded separators are refused; the query goes in query
Transportthe upstream's own TLS and mutual TLS configuration (the one forward uses); verification is never disabled; in production plain HTTP to another host is refused at start-up as for forward
Credentialsnone by default. credentials: "caller" sends the bearer token of the current request, and only when the upstream policy, the transport and the token audience allow it; a refusal is an error, not a silent omission
Correlationthe correlation id and the trace of the current request travel with every call
DeadlinetimeoutMs per call, at most (and by default) http.limits.upstreamResponseTimeoutMs
Cancellationsignal (an AbortSignal); and when the client of the current request disconnects, the calls made for it are aborted
ResponseJSON (or responseType: "text"), read up to maxResponseBytes (default http.limits.maxUpstreamResponseBytes); redirects are never followed
Methodsget, post, put, patch, delete return the parsed body; call returns { status, headers, data }

Failures#

Every failure is an UpstreamCallError with service, kind and, for an answer of the service, status and the parsed problem. Left unhandled it becomes a stable problem that never contains the service's response body:

kindWhat happenedProblem when unhandled
status (404)the service answered 404404 PSO_UPSTREAM_NOT_FOUND
status (409)the service answered 409409 PSO_UPSTREAM_CONFLICT
status (other 4xx, 3xx)the service refused the request502 PSO_UPSTREAM_REJECTED
status (5xx), invalid_responsethe service failed or answered something else than JSON502 PSO_UPSTREAM_BAD_GATEWAY
timeoutno answer within the deadline504 PSO_UPSTREAM_TIMEOUT
unavailablethe service could not be reached503 PSO_UPSTREAM_UNAVAILABLE
tlsthe certificate or the handshake was rejected502 PSO_UPSTREAM_TLS
response_too_largethe answer exceeds the limit502 PSO_UPSTREAM_RESPONSE_TOO_LARGE
policy, unknown_servicerefused before anything was sent500 PSO_UPSTREAM_POLICY, 502 PSO_UPSTREAM_UNKNOWN_SERVICE

An action that knows what a downstream answer means translates it on purpose:

Limits: one attempt per call (no retries, no circuit breaker), no distributed transaction and no saga: if the second call fails after the first one changed data, undoing it is the application's design decision.

The service prefix outside the workspace: PSO_UPSTREAM_<NAME>_PREFIX#

With the workspace file the orchestrator knows each service's endpoint prefix. In a container there is no workspace file: the address comes from PSO_UPSTREAM_<NAME> and the prefix from PSO_UPSTREAM_<NAME>_PREFIX. Both forward and UpstreamClient put that prefix in front of the path.

In a deployment you write by hand, set both for every service that has a prefix. Without the prefix variable every forwarded path misses it and the service answers 404 for routes that work in development.

Service and guard names checked by the compiler#

writes src/pso-types.d.ts from pso.workspace.json and the guards of the project. From then on metadata.service, metadata.services, security.guard, Upstream.forward and UpstreamClient accept only names that exist, in the editor and in npm run typecheck. It is optional: without the file every string is accepted, as before, and pso validate and start-up keep checking either way. Run it again after adding a service or a guard (pso types --check in a pipeline).

Common mistakes#

  • Raising the timeout instead of fixing the slow service.
  • Forgetting that a route's metadata.service must equal the service the action forwards to (otherwise a 500 programming error).
  • Declaring a service in the workspace but not setting PSO_UPSTREAM_* in production.
