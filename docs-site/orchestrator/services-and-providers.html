Services and providers

Injectable classes that hold logic belonging to the orchestrator - how to create them, inject them into controllers and into each other, share them between modules, and what should not live in them.

What a provider is#

A provider is a class the orchestrator creates for you, once, and hands to whoever asks for it in a constructor. "Service" is the usual name for a provider that holds logic. Anything you list in providers of MODULE.pso.ts is a provider; nothing is discovered by scanning.

Why it exists#

A controller should read the request and return a result. If it also composes several upstream calls, reshapes responses and applies rules, it becomes impossible to test and to reuse. A provider gives that logic a home with a name, and the container takes care of creating it and passing it where it is needed, so no controller builds its own dependencies.

When to use it, and when not to#

Put it in a providerKeep it out
composing calls to several upstream services into one public responsedomain rules and persistence: they belong to the microservice that owns the data
mapping or shaping data for the public APIanything that needs a database of its own (the orchestrator has none)
rules the orchestrator itself owns (for example, which fields the public API exposes)secrets handling: read them through configuration, never hard-code them
a business validator that needs another providerrequest parsing: that is the controller's job

4. Share across modules#

Export from the module that owns the provider, import that module from the one that needs it:

BillingController may now ask for PricingService in its constructor. A dependency that is not local, not exported by an imported module and not built in (Upstream) stops validation with PSO_MODULE_006.

5. The built-in Upstream#

Calling another service is the one dependency you never declare: add private readonly upstream: Upstream to a constructor and use forward(...). Unknown services and failures turn into 502, 503 or 504 problems (upstream clients).

What happens when it starts#

  1. pso validate (and the start-up) check, without running your code, that every constructor dependency resolves (PSO_MODULE_006) and that providers do not depend on each other in a circle (PSO_MODULE_007, reported as A -> B -> A).
  2. At start-up the container creates the providers listed in each module and the controllers, in dependency order.
  3. Business validators declared on DTOs are providers too, and are resolved at that time. One that is not listed in the module providers stops the start-up with the route and the class name.

A failure at either step means nothing started: the application never half-works.

Anti-patterns#

Do notWhyDo instead
new PricingService() inside a controllerthe container cannot see it, tests cannot replace itdeclare it in the constructor
keep the current user or request in a provider fieldproviders are shared by all requestspass it as an argument; the verified principal of the request is injected into a controller action with @CurrentPrincipal()
a provider that stores orders in memory "for now"the orchestrator is stateless and may run in several copiesthe owning microservice stores the data
a circular pair (A needs B, B needs A)rejected before startextract the shared part into a third provider
listing a class twice, or in two modules, to "fix" resolutionhides the real ownershipexport from one module and import it

Troubleshooting#

MessageMeaning
PSO_MODULE_006 Dependency cannot be resolvedthe constructor asks for a class that is not a provider of this module, not exported by an imported module and not built in; add it to providers or imports
PSO_MODULE_007 Circular provider dependencythe message shows the cycle; break it
PSO_MODULE_008 Imported module not foundimports names a module that does not exist under src/modules
a constructor parameter arrives undefinedthe class is missing @Injectable(), or the project is not compiled with emitDecoratorMetadata

Production considerations#

Providers live as long as the process. Release resources (timers, connections) in a graceful shutdown hook of your own, not in constructors. Keep constructors fast and side-effect free: the container creates providers before the listener opens, so slow work delays readiness.

Providers, hooks and configuration files: what each one is#

A service, a provider and a hook belong to a module and live in its folders; configuration is application-wide and lives in src/.app/. None of them is scanned: a file takes part in the application only through an explicit declaration or an ordinary import.

ArtifactGeneratorWhat it isHow it becomes active
Module servicepso make:service <module> [name]a class in src/modules/<module>/services/ that coordinates the module's worklisted in providers of that MODULE.pso.ts (the generator does it)
Providerpso make:provider <name> --module <module>an @Injectable() class in src/modules/<module>/providers/, typically the call to a microservicelisted in providers of the module (the generator does it); another module uses it through exports / imports
Lifecycle hookpso make:hook <name> --module <module>a provider in src/modules/<module>/hooks/ that implements onReady and/or onShutdownlisted in providers of the module; a hook nobody lists never runs
Configurationpso make:config <name>a plain module in src/.app/configs/ that reads its values onceimported where it is needed; the framework neither loads nor injects it
Shared codenoneplain classes and functions of no single module, in src/shared/imported where needed; listed as a provider only if something injects it

Lifecycle hooks#

WhenIf it throws
onReadyonce, after every start-up step succeeded and the listener is bound, just before the application reports ready. Hooks run one at a time, in module order and, inside a module, in the order of providersstart-up stops (PSO_HOOK_FAILED): everything acquired is released, the hooks that had started get onShutdown, and the process never reports ready
onShutdownonce during shutdown, after the running requests finished (or the grace period ended) and before the framework releases its own resources; reverse order of onReadylogged, and the shutdown continues

A hook's constructor dependencies are injected like any provider's (other providers of the module, Upstream, UpstreamClient, Dispatch). Hooks are for start and stop work (warming a cache, announcing the instance, flushing a buffer): per-request behaviour belongs in a guard, a middleware or a filter. To verify: start the orchestrator and look for hook ready and lifecycle hooks ran before orchestrator listening in the log.

Configuration files#

It is application configuration, read when the module is first imported. Framework settings (limits, security, logging, dispatch) are not set there: they live in pso.config.json and are listed by pso config:list. In a Spring service pso make:config cache --service catalog writes a @Configuration class, which Spring's component scan finds like any bean of the service.
