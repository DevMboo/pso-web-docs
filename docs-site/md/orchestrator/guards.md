# Guards

> Authentication and authorization checks that run before a route's action, including the built-in jwt guard.

<!-- pso:structure-note -->
> [!NOTE]
> Examples on this page use the 0.1 orchestrator layout (`src/routes/<module>/`, `src/guards/`, `src/contracts/`), which existing
> projects keep. In the official structure of new projects the same files are in `src/modules/<module>/` (`routes/ROUTES.pso.ts`,
> `controllers/`, `services/`, `providers/`, `dto/`) and in `src/.app/` (`guards/`, `middlewares/`, `filters/`, `contracts/`); what the
> page describes works the same way. See [TypeScript orchestrator structure](architecture/typescript-orchestrator.md).

A guard is a function exported as the default of a `*.guard.ts` file. Its **name** is the file name without `.guard.ts`.

## The built-in `jwt` guard

The framework provides the `jwt` guard (package `@pso/security`). You do not write verification code; the generated file is only:

```typescript title="src/guards/jwt.guard.ts"
import { JwtGuard } from "@pso/security";
export default JwtGuard.create();
```

If the file is absent the guard is registered automatically. Configuration lives in `pso.config.json` ([Security configuration](security/security-configuration.md)). An optional policy function adds an authorization decision after verification:

```typescript
export default JwtGuard.create({ policy: (p) => p.hasRole("staff") });
```

## Custom guards

```typescript title="src/routes/users/guards/users-key.guard.ts"
import type { Guard } from "@pso/http";

const guard: Guard = (req) => (req.headers["x-key"] === "k" ? true : { allow: false, status: 401 });
export default guard;
```

A guard returns `true` (allow), `false` or `{ allow: false, status: 401 }` (unauthenticated), `{ allow: false, status: 403 }` (forbidden), or `{ allow: true, principal }` to establish the caller's identity so declared scopes and roles are enforced by the framework. A project `jwt.guard.ts` that does not use `JwtGuard.create()` is **rejected by default**. To replace JWT verification, declare `security.authentication.provider: custom`, identify `customProvider` and use `CustomGuard.create`; see [Custom guards](security/authentication.md#custom-guards). A module-local guard for an additional condition does not replace the framework JWT verifier.

## Where guards live

- Global: `src/guards/*.guard.ts`.
- Module-local: `src/routes/<module>/guards/*.guard.ts`. Names share one namespace; a duplicate stops start-up.

## Using a guard

In `ROUTES.pso.ts`: `security: { guard: "jwt", scopes: ["users:read"], roles: ["admin"] }`, or `guards: ["a", "b"]` (all must pass). With decorators: `@UseGuards("jwt")`, `@RequireScopes("users:read")`, `@RequireRoles("admin")`, `@Public()` and, for the identity, `@CurrentPrincipal()` ([Authorization](security/authorization.md)). Requirements add up across module, controller, action and route; a declaration can never weaken what a decorator demands (`PSO_ROUTE_007`), and an unknown guard name is `PSO_ROUTE_008`. A route with no policy inherits the default `jwt` guard.

```bash
pso make:guard authenticated            # src/guards/authenticated.guard.ts
pso make:guard users users-key          # module-local
```

Generated custom guards deny by default (`() => false`); replace the body with real verification.

## Order of evaluation

Guards run in declared order and establish the principal; then scopes and roles are evaluated centrally (`401` vs `403`); then middleware; then the action.

## What generating a guard does

Expected output:

```text evidence="expected"
$ pso make:guard authenticated
created    src/guards/authenticated.guard.ts

$ pso make:guard orders orders-key --service gw
created    src/routes/orders/guards/orders-key.guard.ts
```

and the generated file denies everything until you replace the body:

```typescript
import type { Guard } from "@pso/http";

// Deny by default: replace with real verification.
const guard: Guard = () => false;
export default guard;
```

A route that names a guard with no matching file is `PSO_ROUTE_008`.

## What a guard decision looks like to the caller and in the log

For the built-in `jwt` guard (expected):

```text evidence="expected"
no token                              -> 401  WARN [security] authentication failed  reason=missing_header route="GET /customers"
valid token, missing scope            -> 403  WARN [security] authorization denied  missing=scope:customers:read route="GET /customers"
```

A custom guard returns `false` or `{ allow: false, status: 401 | 403 }` to refuse; the response is the standard problem for that status.

## Variations

| You want | Do |
|---|---|
| the standard JWT check | `JwtGuard.create()` (generated by default); configure issuer, audience and keys |
| an extra authorization rule | `JwtGuard.create({ policy: (p) => p.hasRole("staff") })` |
| an API-key check for one module | a module-local guard in `src/routes/<module>/guards/` |
| to replace JWT verification entirely | a custom `jwt` guard **and** an explicit `custom` provider declaration; an undeclared replacement stops start-up ([authentication](security/authentication.md)) |

## Common mistakes

- Leaving the generated `() => false` in place and wondering why everything is `401`.
- Returning `true` for "unknown" states: fail closed.
- Doing authorization with scopes by hand inside actions: declare them on the route.

## Troubleshooting

| Symptom | Cause | Check | Fix |
|---|---|---|---|
| `PSO_ROUTE_008` (unknown guard) | the route names a guard that is not defined, often a typo | `pso validate` shows `available:` | use an existing name; never remove the guard to silence it |
| `401` `PSO_AUTH_UNAUTHORIZED` | no token, a malformed token, or issuer, audience, algorithm or expiry do not match | the gateway log line for the request, and `pso security:validate` | send a valid token; align `PSO_JWT_ISSUER` and `PSO_JWT_AUDIENCE` |
| `403` `PSO_AUTH_FORBIDDEN` | the token is valid but lacks the route's scope | the gateway `warn` line "authorization denied" names the missing scope | issue the scope, or correct the route's `scopes` |
| the orchestrator refuses to start | the guard is used but issuer, audience or a key source is missing | `pso security:validate` | set `PSO_JWT_ISSUER`, `PSO_JWT_AUDIENCE` and one key source ([keys](security/keys-and-pem.md)) |

The first three were reproduced on a real workspace ([Validation errors, one by one](reference/diagnostics-catalog.md)); the log line of the fourth is in [Build a CRUD API](tutorials/crud-api.md).
