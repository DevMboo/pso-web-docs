# Orchestrator architecture

> Node.js + TypeScript, compiled, declarative modules, one public entry point - what the orchestrator does, what it deliberately does not, how a request travels through it, and how to deploy and scale it.

The orchestrator is the single public entry point of a workspace. It validates tokens, applies route policy and forwards to services. It holds **no domain logic**; that belongs in the microservices.

```tree title="The orchestrator source layout"
gateway/
  src/
    main.ts  # generated: the minimal bootstrap
    guards/jwt.guard.ts  # generated: the global guard
    middlewares/  # generated: empty, a named extension point
    filters/  # generated: empty, a named extension point
    routes/
      users/  # manual: one folder per module
        MODULE.pso.ts  # generated by make:module
        ROUTES.pso.ts  # generated by make:module
        users.controller.ts  # generated by make:controller
        users.service.ts  # optional
        dto/  # optional
        guards/  # optional
    contracts/  # generated: *.contract.json files
  dist/  # generated: compiled output, what actually runs
```

## What it is responsible for

| Responsibility | How |
|---|---|
| deciding what is reachable | the `ROUTES.pso.ts` registries; anything else is `404` |
| authenticating and authorising | JWT guard, scopes and roles per route |
| protecting itself and the services | body, header and connection limits, rate limiting, request timeouts |
| forwarding | `Upstream.forward` to a declared service, with header hygiene and an optional bearer token |
| answering consistently | RFC 9457 problems with stable codes and a correlation id |
| being observable | logs, metrics, traces ([logging](devops/logging.md), [observability](devops/observability.md)) |
| validating the bodies it owns | `@Body(Dto)` ([DTO validation](orchestrator/dto-validation.md)) |

## What it is not responsible for

Business rules, persistence, and anything that must survive a restart. If you find yourself adding a database to the orchestrator, the logic probably belongs in a service ([controller or service?](decisions/controller-or-service.md)). This is also why it has no transactional outbox ([why](decisions/why-no-typescript-outbox.md)).

## Key properties

- **Compiled TypeScript.** Decorators and constructor metadata cannot run directly in Node, so the orchestrator is built with `tsc` (CommonJS, `experimentalDecorators`, `emitDecoratorMetadata`). `npm run dev` and `pso dev` compile and then start `dist/main.js`.
- **Declared exposure.** Only routes declared in `ROUTES.pso.ts` of a valid module exist ([Routing](orchestrator/routes.md)).
- **Framework-owned runtime.** `@pso/http` provides decorators, `defineRoutes`, dependency injection, the HTTP server, the proxy, rate limiting and logging. `@pso/core` provides `defineModule`, validation and discovery.
- **Declared upstreams.** Services come from `pso.workspace.json` in development and from `PSO_UPSTREAM_<NAME>=host:port` in production; there is no port scanning.
- **Stateless.** Any instance can serve any request, which is what lets you run several behind a load balancer.

**HTTP request lifecycle.** The order in which the PSO orchestrator runtime handles a request, as implemented in @pso/http.

1. **HTTP request** (arrives at the orchestrator): The runtime assigns a server-side correlation id (a client-supplied x-correlation-id is never trusted) and starts structured logging for the request.
2. **Rate limit** (per client address): A bounded token bucket keyed by the socket address (X-Forwarded-For is not trusted). Excess requests get 429 with Retry-After. Health probes are exempt. This is one protection layer, not DDoS protection.
3. **Route registry** (ROUTES.pso.ts): The request is matched by method and path against the validated routes only. An undeclared path, or a decorated method that is not in ROUTES.pso.ts, answers 404.
4. **Authentication** (guard: jwt): The guard named by the route verifies the bearer token: asymmetric signature, issuer, audience, expiry, not-before and subject. With no key configured it denies everything. Failure answers 401.
5. **Authorization** (scopes): The same guard checks the scopes required by the route. A valid token without the required scope answers 403.
6. **Middleware** (named, per route): Middleware listed on the route runs after the guards, so it only ever sees authenticated requests (public routes excepted). A middleware may end the response.
7. **Body and parameters** (@Param @Query @Body): Path and query parameters are read and, when the action declares @Body(), the JSON body is parsed with a size limit (400 invalid JSON, 413 too large, 415 wrong content type). Schema validation of DTOs is not built in.
8. **Controller** (the action): The decorated action runs. It stays thin: it delegates to a service or forwards to an upstream service with the injected Upstream provider.
9. **Service** (provider): Providers declared in MODULE.pso.ts hold the logic that belongs to the orchestrator. Domain logic belongs in the microservices.
10. **Response** (JSON + correlation id): The returned value is serialized as JSON (201 for POST, otherwise 200). Errors never leak internals: exception filters can handle them, otherwise a generic 500 is returned.
## How a request travels

```flow title="Request pipeline of the orchestrator"
[request] client -> limits and rate limit -> route registry -> JWT and scopes -> middleware -> DTO validation -> controller action
[forward] controller action -> Spring service | token checked again
```

Every stage that can refuse a request has its own status and code; see [Request and response lifecycle](orchestrator/request-lifecycle.md) for the table, with real examples of `401`, `403`, `404` and `503`.

## Deploying and scaling

| Concern | Guidance |
|---|---|
| instances | run as many as you need; no sticky sessions are required |
| rate limiting | the default budget is per instance; use the Redis provider when instances must share one ([decision](decisions/local-or-distributed-rate-limit.md)) |
| upstream addresses | `PSO_UPSTREAM_<NAME>=host:port`; in production a remote upstream needs TLS unless explicitly marked `allowPlaintext` ([service identity](security/service-identity.md)) |
| configuration | environment variables and `pso.config.<env>.json` ([configuration](concepts/configuration.md)) |
| health | `GET /health/live` and `GET /health/ready` (public) |
| shutdown | on `SIGTERM` it stops background work and closes connections; take it out of rotation first ([lifecycle](concepts/runtime-lifecycle.md)) |

## Common mistakes

- Running `ts-node`/`node` on the sources: always run the compiled `dist/main.js`.
- Putting domain logic in controllers "because the gateway is right there".
- Letting the orchestrator reach services through addresses that are not declared.
