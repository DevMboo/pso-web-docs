The reference Product CRUD

File by file, the Product CRUD that pso create service and pso create orchestrator generate - endpoints, security, validation, persistence, the request lifecycle from the orchestrator to PostgreSQL, how to run and call it locally, in Docker and from Studio, how to remove it and how to generate another resource the same way.

Status

Implemented and verified. Generated by the distributed CLI into a new workspace, built, started with real PostgreSQL and the identity provider in Docker, and called through the orchestrator and directly: every status below was observed, the data survived a restart, and the generated tests pass.

pso create service catalog generates a working Product API in the layered Java structure; pso create orchestrator gateway generates the matching products module and binds it to the service that serves /products. Both are examples to keep or remove: nothing in the framework depends on them, and --template empty creates the same projects without them.

The resource#

FieldTypeRules
idUUIDassigned by the service
skustringrequired, 3-64 characters, upper-case letters, digits and inner hyphens (KB-100), unique (database constraint)
namestringrequired, 1-120 characters
descriptionstringoptional, at most 2000 characters
pricedecimalrequired, >= 0, at most 10 integer digits and 2 decimals (NUMERIC(12,2), BigDecimal; sent as a string)
activebooleandefaults to true
createdAt, updatedAttimestampUTC (TIMESTAMPTZ), set by the service

Endpoints#

Method and path (orchestrator)ScopeAnswers
GET /products/optionspublic200: the sortable and filterable fields and the page limits (no data, no backend call)
POST /productsproducts:write201 + Location, 400, 401, 403, 409 (duplicate SKU)
GET /products?page&size&sort&sku&name&activeproducts:read200 (a page), 400 (bad page, size or sort field)
GET /products/{id}products:read200, 400 (not a UUID), 404
PUT /products/{id}products:write200, 400, 404, 409
DELETE /products/{id}products:write204, 404

The microservice serves the same API under its prefix (/catalog/products), checks the token and the scopes again, and is reachable only inside the workspace network: the browser and other clients use the orchestrator. Every error is an RFC 9457 problem (application/problem+json) with the same shape on both sides; a duplicate SKU is 409 conflict with the detail "a product with this sku already exists" (the submitted value is not echoed).

How a request flows#

  1. The orchestrator matches the route in routes/ROUTES.pso.ts; the jwt guard validates the token and the scope (401 / 403 here).
  2. The controller validates parameters and the body with the DTO decorators (400 before anything is called) and delegates to the service.
  3. ProductProvider calls the service by name (UpstreamClient, the binding constant PRODUCT_SERVICE) with the caller's token (credentials: "caller") and the correlation id; it translates the service's 404 / 409 / 400 into the same problems.
  4. In the microservice the PSO security starter validates the token again, @PreAuthorize checks the scope, @Valid validates the record, and ProductService runs the operation in a transaction.
  5. PostgreSQL enforces the constraints (the unique SKU among them); pagination, sorting and filters run in the query.
  6. The mapper returns the public response; the entity never leaves the service.

Binding the module to its service#

The orchestrator finds the service that serves /products in pso.workspace.json; no service name is assumed. Created before the service, the module still compiles and starts, pso validate warns PSO_CRUD_UNBOUND, and its routes answer 502 (unknown_service) while the start-up log names the missing service and the fix; pso create service binds it as soon as the service exists. Running it#

Locally without the containers of the projects: ./mvnw spring-boot:run in catalog against a PostgreSQL database (DB_URL, DB_USER, DB_PASSWORD; the h2 profile does not apply to this service) and npm run dev in gateway. ./mvnw test and npm test run the generated tests. The database password and the development user are generated per workspace into .infra/ and never written into source or into the collection.

In Studio the collection's requests go to the orchestrator (edge:api): that is how clients use the API. A request sent directly to the microservice is labelled as such and needs a token of its own: it is for diagnosing the service, not for clients.

Requests and answers#

Real requests through the orchestrator of a generated workspace, and the answers it gave (identifiers, timestamps and correlation ids as returned; the token is a development user's). The microservice was stopped for the last one.

Removing it#

Delete the files listed above (the project's docs/reference-crud.md lists them for the project) and, if the table holds nothing you need, add a migration that drops it (pso make:migration drop-products) instead of editing V1. Remove the products module directory from the orchestrator. pso validate confirms the result.

SymptomCauseFix

403the token lacks products:read / products:writegrant the scope to the user in the identity provider
