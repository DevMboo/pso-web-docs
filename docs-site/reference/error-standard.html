Error standard (RFC 9457)

One error format for the TypeScript orchestrator and every Spring service: Problem Details with stable PSO codes.

Every error the framework itself produces (not your application's domain errors) is application/problem+json with the same members in TypeScript and Java. The catalog is a language-neutral contract; both runtimes have tests that fail when their catalog differs from it.

MemberMeaning
typestable URI reference of the problem kind (urn:pso:problem:<slug>); it is an identifier, not a URL to fetch
title, detailfixed, safe text. Never an exception message, a stack, a host path, a URL with credentials or user input
statusthe HTTP status
instancethe request path of this occurrence, without the query string
codethe stable PSO code programs should switch on
correlationIdthe request correlation id; also the X-Correlation-ID header
errorsvalidation problems: a list of { field?, message }
errordeprecated legacy short code, kept so existing clients keep working
fieldsdeprecated, Java validation only: { field: message } map of the former template handler

Codes#

CodeStatusWhen
PSO_HTTP_BAD_REQUEST400the request cannot be understood (also type mismatches)
PSO_VALIDATION_FAILED400bean validation failed; see errors
PSO_HTTP_INVALID_JSON400the body is not valid JSON
PSO_HTTP_REQUEST_ABORTED400the client closed the request early
PSO_HTTP_MALFORMED_MULTIPART400a multipart/form-data body that is not well formed (no boundary, truncated, bad part headers)
PSO_AUTH_UNAUTHORIZED401missing or invalid credentials; WWW-Authenticate: Bearer (error="invalid_token" when a token was presented)
PSO_AUTH_FORBIDDEN403authenticated but not allowed (scopes, roles, method security)
PSO_HTTP_NOT_FOUND404no such route (undeclared routes do not exist)
PSO_HTTP_METHOD_NOT_ALLOWED405Spring services; the Allow header is kept
PSO_HTTP_PAYLOAD_TOO_LARGE413body over the limit
PSO_FILE_TOO_LARGE413an uploaded file over its declared maxSize (orchestrator) or the service upload limit (file uploads, storage)
PSO_HTTP_UNSUPPORTED_MEDIA_TYPE / PSO_HTTP_MULTIPART_DISABLED415wrong content type / multipart not enabled
PSO_RATE_LIMITED429rate limit; see Retry-After
PSO_HTTP_HEADERS_TOO_LARGE431request headers over the limit
PSO_INTERNAL_ERROR500anything unexpected; nothing about the failure is returned
PSO_UPSTREAM_POLICY500an outbound call was refused by the destination policy
PSO_UPSTREAM_BAD_GATEWAY, PSO_UPSTREAM_RESPONSE_TOO_LARGE, PSO_UPSTREAM_UNKNOWN_SERVICE502invalid upstream response / response over the limit / route names an unconfigured service
PSO_UPSTREAM_TLS502the TLS connection to an upstream could not be verified (untrusted, expired or wrong-name certificate, or the upstream rejected the client certificate); see Service identity
PSO_UPSTREAM_UNAVAILABLE, PSO_SERVER_BUSY, PSO_RATE_LIMIT_UNAVAILABLE, PSO_STORAGE_UNAVAILABLE503upstream unreachable / concurrency limit (also MAX_CONCURRENT_UPLOADS) / shared limiter down with a fail-closed policy / the file storage backend failed (provider detail stays in the server log)
PSO_UPSTREAM_TIMEOUT504upstream did not answer in time

An error raised deliberately by application code with HttpError(status, message) keeps its status and its message as detail; its code is PSO_HTTP_ERROR_<status>. Custom guards and filters can still write their own responses.

Where it comes from#

  • TypeScript orchestrator (@pso/http): every framework failure path, including request-size, upstream, rate-limit, guard and routing errors, header overflow (431) and concurrency shedding.
  • Spring services: PsoProblemAdvice (all MVC failures, bean validation, unexpected exceptions), PsoSecurityProblemAdvice plus the entry point and access-denied handler of the security starter (401/403 from the filter chain and from @PreAuthorize), PsoHttpProblemAdvice (PsoHttpClient failures; the remote's message and body are never echoed), and the request-limit filters. Define your own bean of the same type to replace one, or add an @ExceptionHandler for your domain exceptions.

Migration#

The generated Spring template no longer contains an ApiExceptionHandler; existing services can delete theirs once they accept the standard body (the legacy error member and the Java fields map are still present). Content-Type changes from application/json to application/problem+json; clients that read error keep working.

Reading a problem#

MemberUse it to
codebranch in code (stable; the legacy error member is kept for older clients)
statusthe HTTP status (also in the response line)
correlationIdfind the server log lines; also in the x-correlation-id header
errorsshow field messages to a user (validation)
detaila human sentence; constant for framework errors, the application's own text for HttpError

Answers of upstream services#

When the orchestrator (UpstreamClient) or a Spring service (PsoHttpClient) calls another service and the application does not handle the outcome, the answer is one of these, identical in both runtimes. The upstream's own body is never forwarded.

Legacy codeStatusCodeWhen
upstream_not_found404PSO_UPSTREAM_NOT_FOUNDthe upstream answered 404: something the request depends on does not exist
upstream_conflict409PSO_UPSTREAM_CONFLICTthe upstream answered 409
upstream_rejected502PSO_UPSTREAM_REJECTEDthe upstream answered another 4xx (or a redirect): it refused a request this service made
bad_gateway502PSO_UPSTREAM_BAD_GATEWAYthe upstream answered 5xx or something that could not be read

Upstream.forward is different by design: it relays the upstream's status and body to the client unchanged. To give a downstream outcome a meaning of your own, catch UpstreamCallError (upstream clients) or PsoHttpException (HTTP client) and raise your own error.

Common mistakes#

  • Branching on detail text.
  • Showing detail of a 500 as if it explained the cause: it is deliberately generic.
  • Ignoring correlationId when reporting a problem.
